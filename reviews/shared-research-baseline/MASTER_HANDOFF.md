# AI 游戏工厂：完整会话结论与 Codex 项目准备总纲

**版本**：V1.0｜**冻结日期**：2026-10-21｜**定位**：项目准备与市场审查，不是开发完成报告

> **给 Codex 的首要指令**：严格执行本文件的范围与证据准则。第一阶段只研究、审计和制作每个项目的完整施工档案，不要直接启动某一款游戏的代码开发，不要重新增加平台，也不要把候选游戏误写为已验证产品。

## 0. 一页执行摘要

### 0.1 目标

建立**自有 AI 游戏制造系统 + 自有游戏 IP 组合 + 外部发行/授权渠道**的资产型公司。AI Coding 如同可编程制造设备，游戏机制、关卡算法、美术规范、自动测试组件是可复用的「材料」，不同游戏是可以独立授权、运营、出售的产品资产。

主要追求：可复制的制造效率、持有知识产权、通过外部发行商/分销网络获取用户与收入、可重复授权、长期现金流。**不是**按小时开发、一次性客户定制外包、靠堆数量卖低质源码。

### 0.2 冻结范围：6 个目标对象（不允许擅自扩大）

- **网页与授权（4）**：Coolmath Games（非独家授权买家）、CrazyGames（自有流量及测试）、Poki（精选发行及推广）、Playgama（多站点分销）。
- **移动发行（2）**：Azur Games（移动测试及买量）、TapNation（移动发行、推广与运营）。
- **辅助工具，不计入发行目标**：itch.io 可以托管 Demo；Google Play / App Store 是移动端交付终点或发行商使用的商店，不是本轮单独研究的商业合作对象。
- **二轮暂缓**：Steam、Epic、Roblox、微信小游戏、抖音小游戏、GameDistribution、GamePix、Voodoo、Homa、SayGames 等。其曾在对话中讨论过，但本轮不进入项目数量 KPI；必要时作为技术/商务背景引用。

### 0.3 冻结候选：10 个游戏项目家族

G01 箭头路径消除；G02 分类排序收纳；G03 合成订单+轻经营；G04 逻辑图层与机关解谜；G05 陷阱平台跳跃；G06 物理驾驶挑战；G07 自动化经营/放置成长；G08 群体答案问答竞技；G09 物理合成与空间管理；G10 角色装扮与创造。

这些是**项目家族和工作编号，不是已经完成的完整 GDD，也不是 10 款保证可以发行的游戏**。

### 0.4 批次（项目准备，非立即批量开工）

- P0：G01、G02、G04（规则型解谜，共享网格/状态/求解/关卡）。
- P1：G03、G07、G08（经营、经济、知识内容与成长）。
- P2：G05、G06、G09、G10（平台控制、连续物理、特殊美术资产）。

每批先形成可施工文档，经过独立审查才允许批准开发。允许多个 Codex 会话并行做研究，但必须使用统一 ID、证据库与质量标准。

### 0.5 最关键的商业结论

1. **先有市场证据、再做项目施工图、最后开始开发**；不能让开发 Agent 重新猜测游戏形态。
2. **发行≠买量≠授权采购≠收入**。六家提供不同价值，必须分别评价。
3. **热榜 ≠ 当前采购需求 ≠ 新作回报率**。对标作品只证明玩家偏好线索，不证明新游戏成功概率。
4. **IP 可交易但重复授权能力尚未被证明能规模化**。Coolmath 官方确有非独家采购；Playgama 有多站点分发；Poki 独家可能与非独家铺货冲突；移动发行协议必须审查权利。
5. **AI 降低编码成本并不自动提升利润**，美术、关卡体验、质量控制、发行审核、获客是关键瓶颈。
6. 先做项目库与 3–5 项独立可施工项目，不立刻造通用引擎，也不为 6 个渠道机械制作 24–30 款互不相关游戏。

## 1. 会话演变：为什么最后收敛到这里

1. **起点**：把 AI Coding 当作 3D 打印，尝试从底层「材料」构造游戏，实现规模化制造，委托海外渠道分销。初期偏向不用现成游戏引擎。
2. **技术方案第一版**：TypeScript/Canvas、GameSpec、规则组件、自动试玩；形成了概念性的 AI Game Foundry 和示范代码。
3. **Godot 讨论**：发现游戏引擎本身已是通用制造底座。结论变为不必重写渲染/物理全部基础设施；更独特的价值在于**AI 可理解的机制模块、约束装配和验证系统**。
4. **量化选品**：研究热门游戏、变体实验、游戏数据、成本和 ROI。识别 Arrow/Sort/Block、陷阱闯关、物理驾驶、经营成长几个可复用家族。
5. **商业模式修正**：最初偏重 HTML5 投稿和广告分成；随后明确用户不想「自助上架后等流量」，而是要有采购者/经销商/推广方。区分非独家授权、独家发行、完全买断、广告分销、移动发行商付费测试。
6. **产业覆盖修正**：曾扩展至移动、PC、Roblox、国内小游戏做比较；之后根据首轮资源限制，**主动收敛为 4 个网页渠道 + 2 个移动发行方**。
7. **完整施工要求**：用户不接受只凭一种点子生成单款游戏，要求每个平台有 3–5 个有具体对标和证据的候选，且每个入选项目必须形成「可让 Codex 独立施工」的全套文档。
8. **Vector Shift**：曾制作 Arrow 方向的 8 关、随后 20 关技术原型、求解器、QA；它证明某些规则引擎的实现可行，但**不是**全局市场选品完成、商业质量认证或本轮唯一游戏。保留为机制实验档案，不强制作为 G01 的正式设计。
9. **最终工作方式**：先平台证据与真实对标 → 每个平台提出 3–5 个候选 → 去重为 10 家族 → 每个独立 GDD/技术/关卡/美术/经济/QA/授权资料 → 审批后才实施。

**已被否决的执行偏差**：自动扩张至 20 多个平台；把小公司定制外包作为主要生意；只做一个演示游戏替代完整项目库；只给「做精致一些」的模糊指令；把买家挂牌价当真实成交价；把某平台总流量当单游戏流量。

## 2. 六渠道逐家定位、准入与需求证据

**事实等级说明**：A = 2026-10-21 重新访问到的官方页面；B = 前面对话引用的官方/第三方资料但本文件没有重检全部细节；C = 个体经验或推断。各渠道联系人、条件、条款都应在正式投稿/签约当日重新检查。

### P01 Coolmath Games（非独家授权采购）

- **价值**：官方表示对于符合要求的作品愿购买**非独家许可**，不是单纯免费上架。正式报价、采购量、购买周期未公开。
- **官方准入**：HTML5；具有逻辑、策略或问题解决元素；无暴力/不雅内容；为其制作的版本移除广告、外链、开发者回传统计；可以在提交时不完全满足所有要求，但要愿意调整。A。[S01]
- **官方入口**：https://www.coolmathgames.com/submit-a-game ；https://developers.coolmathgames.com/
- **热门/对标来源**：官网 Top 10 在本次核查时列 Run 3、Tiny Fishing、Suika Watermelon Game、Cookie Clicker、Moto X3M 等；本周推荐有 Paint Master、Rodha 2。注意该列表不是「近期新作营收榜」。A。[S02]
- **优先方向**：G04 逻辑图层/机关；G09 物理合成；G05 带逻辑的精准闯关；G01 的策略性变体。
- **施工/销售差异**：单独无广告无外链构建；版权清单；授权范围、源代码是否必要、单域名/长期/转授权及付款时间需另问。

### P02 CrazyGames（玩家测试 + 正式发行）

- **价值**：Basic Launch 限量测试，指标达标后可能 Full Launch 并打开广告分成，不是保证推广或固定收购。
- **官方流程**：Basic Launch 7–21 天；至少 7 天并达到 500 次游玩方按正常流程结束；Basic 期间广告及内购变现关闭；关注游戏转化、平均游玩时间、留存。A。[S03]
- **入口**：https://developer.crazygames.com/；技术文档 https://docs.crazygames.com/
- **对标类别**：Arrow Escape / 螺丝整理 / Merge Bake 等解谜，物理驾驶与 3D 动作另为独立类别。网站类别页可以作**存在性/展示证据**，并非可靠单款收益证明。[S04]
- **候选**：G01、G02、G03、G06、G04。
- **风险**：不能从 Basic 获得游戏收入；不能凭达到门槛推断一定有流量或一定正式发行；SDK 在 Full 阶段独立适配。

### P03 Poki（精选测试 + 发行推广）

- **价值**：真人测试、类别流量测试、精选平台与合同推广；受游戏原创性、完成度与技术表现限制。
- **官方准入**：强调质量、玩家适配、技术优化；反对换皮克隆及粗糙 AI 生成游戏。支持原型提交，但玩家 fit → web fit → final review 逐级推进。A。[S05][S06]
- **测试**：每轮 10 份试玩录像；Player Fit 500 玩家，健康参考为平均 3 分钟以上、25% 以上的试玩超过 3 分钟；Web Fit 测类别页面点击/转化；官方建议正式评审前瞄准 ≥65% 的 conversion-to-play 与 ≥5 分钟平均游玩（经营模拟 ≥10 分钟）。这些是平台参考，不是保证录用或跨渠道 KPI。A。[S06]
- **投稿**：https://developers.poki.com/guide/share 需可玩链接/视频、3 张截图、游戏简介及团队资料。[S07]
- **独家风险**：网页独家默认约五年且覆盖 YouTube Playables/Discord 等 Web 形式；移动 App/Steam 不在其默认 Web 排他范围。也可能采用一次性非独家许可但无同等持续推广/分成。必须先谈合同；不要默认可与 Playgama 同时分销。A。[S08]
- **本次官网热门页**：Subway Surfers、Monkey Mart、Blocky Blast Puzzle、Level Devil、Stickman Hook 等；是「当前展示热门」，不等于全部是新作。[S09]
- **候选**：G05、G06、G07、G10，此外 G01 若有显著原创且强完成度也可提出。

### P04 Playgama（多站点分销网络）

- **价值**：一次技术接入，向合作渠道分发，聚合统计及结算。官方网络覆盖是总体流量，不是单款保底。
- **官方流程**：注册开发者 → 集成 Bridge SDK → 上传 HTML5 游戏包 → QA/审核 → 分发合作渠道 → 看报表；SDK 处理广告、存档和站点适配。A。[S10]
- **官网声明限制**：虽然 SDK 兼容一些门户，但 Playgama **不代为向 Poki 和 CrazyGames 投稿**；这些要单独提案。A。[S11]
- **入口**：https://developer.playgama.com/；https://wiki.playgama.com/playgama/quick-start
- **本次 Trending Now**：Piece of Cake: Merge & Bake、Arrow Puzzle、Good Sort Master、Deadly Descent、My Perfect Farm 等；仅能证明近期上榜展示，不是单款 RPM 或收入资料。[S12]
- **候选**：G01、G02、G03、G07、G09、G10。
- **合同点**：要求分渠道展示量、游戏启动量、开发者分成的计算口径与具体协议；独家渠道清单、撤回时效与桥接 SDK 冲突需核实。

### P05 Azur Games（移动发行商）

- **价值**：有条件为原型购买测试流量、评估 CPI/留存、随后提出发行合作；不是自助应用商店。
- **官方投稿表单**：姓名邮箱、游戏名、玩法视频、是否已上架、APK 下载链接、团队和开发平台。官方说明内部评估后才买少量流量，测试留存及 CPI，之后可能发合同。A。[S13]

- **候选**：G01/G02 的移动衍生版、G07、G09（其中哪个最适合需再做适配研究）。

### 六渠道与技术路线

- **网页四家**：首选 2D 轻量项目以 Cocos Creator + TypeScript 实现（也可在项目技术审计中提出 Godot/自研 Canvas 的例外），通过独立 platform adapter 输出不同构建，**不假定某个 Bridge SDK 在所有平台无条件兼容**。
- **移动两家**：根据客户 SDK 条件单独选择 Unity/C# 或其他能满足要求的方案；**不要擅自假设 Cocos 的 Web 游戏直接转换成合格移动测试包**。
- **跨引擎**：共享 GameSpec、数值表、机制数学定义、关卡数据、测试向量、文案和素材规范；不能假设 TypeScript 源码原封不动跑在 C# 环境。

### G01｜Arrow / 路径解谜
- 调查强项：玩法规则容易形式化，能够用搜索算法验证「有解/无解」「最短步数」「分支复杂度」。
- 需要调查：对标游戏真实输入、失败惩罚、生命/提示、各机制引入顺序、奖励和后期变化。
- 候选新机制：相位/颜色状态、条件旋转、障碍变形（须通过玩家试验证明相较基准版有益）。
- 商业风险：2026 年同质化竞争；平台可能因换皮拒绝；Vector Shift 不能因已做出原型而免审。

### G02｜分类/排序收纳
- 子类不能混为一谈：颜色水瓶、货架三消、螺丝拆除涉及不同状态空间和解题反馈。
- 调查关键：何时失败、缓冲槽数量、提示机制、是否随机生成、操作误触与手感。
- 组件资产：拖动/交换、缓冲槽、状态回滚、关卡可解性检查。

### G03｜合成+订单+经营
- 必须反向重建「合成规则—订单—收益—容量—装修/解锁」数据闭环，不能仅做合成手感。
- 需要输出前 30 分钟经济模拟、免费资源供应、瓶颈、虚假成长防护、适度广告机会（符合渠道规定）。
- 较重的美术与数值成本，不能仅凭热门样本就排在最先开工。

### G04｜逻辑机关/层叠
- 不等同于 Arrow 轻微换皮；需有可清楚解释的新规则，如绘制次序/层叠关系/可移动重力/路径控制。
- 与 Coolmath「thinking game」买方条件匹配；重点验证关卡设计和解题满足感。
- 应产出关卡求解器、难度分档、20 关具名规格、关卡作者工具建议。

### G05｜陷阱平台跳跃
- 竞争关键是控制手感、反馈、公平性与低挫败；参考 Level Devil 不可复刻其具体关卡陷阱排列、美术、音效。
- 需定义 tick、碰撞、死亡与复活时间、镜头、操作延迟、关卡重试节奏。

### G06｜物理驾驶
- 不能仅复制 Drive Mad 的车/赛道；先对标操控感与障碍种类，设计独立物理场景逻辑。
- 需要确定是否能使用成熟物理库；拒绝无必要地从头写刚体求解器。
- 原型性能、不同屏幕操控、物理回放一致性是主要难点。

### G07｜经营与放置成长
- 建立订单/资源/工人/升级/产量/时间等经济系统的数值表及可模拟模型。
- 玩法初步成立的最低要求不只是「能点出金币」，而是明确多个可检验的成长决策。

### G08｜群体答案问答
- 需要真实答案语料的来源/授权，不能虚构「全世界最常见答案」的调查排名。
- 可选择原创众包问卷或合规公开数据；多语言与文化差异可能显著影响表现。

### G09｜物理合成
- 确定对象接触、随机生成、队列预告、空间约束、失败判定以及可复现随机种子。
- 物理堆叠模拟与实际手机性能之间的权衡，必须在技术审计中测量。

### G10｜装扮与创造
- 美术资产数量和一致性是首要生产成本，不能因为逻辑简单就认定最便宜。
- 必须定义可用部位、叠层遮挡、衣物约束、风格标签、角色版权和保存分享限制。

## 4. 游戏项目「可施工」的强制交付标准

每个 `games/Gxx/` 必须有**独立内容**，而不是把模板复制十份后改游戏名：

| 文件 | 必需内容 | 准备结束的通过标准 |
|---|---|---|
| `00_Project_Charter.md` | 目标玩家、渠道、商业诉求、范围限制 | 有具体受众和明确目标平台 |
| `01_Market_Evidence.md` | ≥2 个对标、来源、日期、数据口径、反面证据 | 重要事实可追溯，排名/收入不混用 |
| `02_Benchmark_Playthrough.md` | 具体操作、前 30 秒、前 5 分钟、失败/成功、后期循环 | 直接观察与推测分开 |
| `03_Full_GDD.md` | 全流程/游戏规则/状态/教程/成长/失败/胜利 | 不需 Agent 重新猜游戏是什么 |
| `04_Systems_and_Data.md` | 对象、组件、事件、GameSpec、状态机、输入输出 | 数据类型、边界、依赖明确 |
| `05_Levels_Economy.md` | 前 20 关或前 30 分钟内容；数值表；生成与验证 | 不出现「AI 自动生成大量关卡」这种空话 |
| `06_UI_Art_Audio.md` | 每一屏、布局、触控、动画、素材规格 | UI 既有参考亦有可实现规格 |
| `07_Tech_Architecture.md` | 引擎版本、模块与 API、平台适配、构建与性能 | 可由另一工程 Agent 独立落地 |
| `08_OpenSource_Licenses.md` | 源码/资产 URL、许可、维护状态、使用范围 | 不依赖来源不明素材 |
| `09_Implementation_Plan.md` | 任务 ID、前置依赖、I/O、文件、验收 | 任务可以并行且互不冲突 |
| `10_QA_Test_Plan.md` | 单元、模拟、浏览器、真机、玩家体验、回归 | 每条关键规则都有验证方法 |
| `11_Distribution_Business.md` | 发行平台专用版本、合同风险、收益假设 | 不把技术投稿等同取得流量 |
| `12_Falsifiability.md` | 风险、反例、杀死项目条件、证据缺口 | 允许 Kill/Revise 而不是全部通过 |
| `game-spec.json` | 可机读规则、实体、关卡与目标 | schema 校验通过 |
| `tasks.json` | 可机读任务依赖与 DoD | 能自动分配给 Codex 会话 |

**施工门槛**：未在真实对标中观察的关键玩法必须标“自有假设”；核心规则、数据、屏幕、素材、测试中任何一个模块未知，不允许标记 `READY_FOR_BUILD`。工程 Agent 可以选择实现细节，但不可重写产品定义。

### 每款游戏必要的玩家路径

入口/加载 → 3–10 秒可操作引导 → 首局核心行为 → 得到反馈 → 第一胜/第一败 → 复玩 → 新机制 → 中期目标 → 持续成长/挑战 → 存档/退出 → 回归。每个节点必须描述：玩家输入、系统状态变化、视觉音频反馈、展示文案、预期行为指标、异常情况。

### 质量不是「AI 认为很好玩」

- **逻辑**：确定性 seed，单元测试、状态快照、replay、关卡可解性/可达性。
- **体验**：盲测，不提前讲解；测首分钟开始/离开、前三关/前五分钟、误触与挫败原因。
- **表现**：统一美术方向、加载、动画节奏、声音、响应式布局；特意检查简单占位 UI 冒充成品。
- **商业**：平台审核、真实曝光与游戏启动量、可观察收入、开发者实际净回款、渠道归因。
- **知识产权**：不复用商业游戏的专有素材、关卡或代码。玩法思想可研究，表达与资产需要原创或合法授权。

## 5. 技术架构：AI 原生游戏制造，而非必须自研底层引擎

### 5.1 讨论过的路线

- 自研 TS/Canvas：可用于非常轻的 2D Web 游戏；完全自研渲染/物理/资源管线通常不是第一轮最优投入。
- Godot：开源、方便无头构建与 AI 编辑，2D/3D；但部分 Web 兼容或移动发行 SDK 存在适配成本。
- Cocos Creator + TS：**网页/国内小游戏能力可复用**，对当前网页四家及部分移动产物是合理首选；仍须做渠道 SDK QA。
- Unity + C#：对于专业移动发行测试及行业 SDK 更常见；发行商指定 SDK/构建要求优先。
- Phaser / PixiJS / 原生 TS：轻量 Web 的替代路径，应在单项目审计中用实际包体、性能、构建稳定性比较。

**当前暂定**：Web-first 家族优先 Cocos Creator + TS；移动原型按发行商接口要求决定；跨引擎仅共享**引擎中立**的规则数据、资产描述、测试向量，不承诺「一套 TS 源码运行所有端」。

### 5.2 最小通用制造层

```text
Research/Evidence → Benchmark Playthrough → GameSpec (versioned schema)
                                   ↓
                     Rule/Mechanic Registry
                                   ↓
                   Game-Specific Construction Plan
                                   ↓
                    Engine Adapter (Cocos/Unity/...)
                                   ↓
                  Headless Simulation + Browser QA
                                   ↓
                Platform-Specific SDK / Release Builds
                                   ↓
                 Channel Data + IP/License Ledger
```

通用组件候选：网格与图、对象状态、输入事件、碰撞、排序/匹配、关卡生成/求解、经济数值、存档、回放、QA、平台适配、统计事件 Schema。

### 5.3 Claude Code Game Studios 的正确角色

以前讨论的 `Donchitos/Claude-Code-Game-Studios` 属于**Agent 角色、技能与项目开发流程框架**，不是游戏引擎，不是现成商业化工厂。它可作为 Codex Agent 分工、QA 和开发流程参考；迁移命令/Hook 需实际验证，不能复制文件就假定兼容。应独立审查仓库当前许可证与活跃状态。

### 5.4 已做过的 Vector Shift 与历史附件

- 历史会话中有 `AI_Game_Foundry_Benchmark_Research_Skill_2026-10-21.zip`、`Vector_Shift_v0.2_20_Level_Game_Source_QA.zip` 等资料。
- **地位**：机制、关卡求解和工具链的原型参考；不证明市场适配、原创差异能提升留存、平台审核通过、销量或 ROI。
- **本次 Codex 任务**：可以阅读其思路并独立审查；禁止将它直接定为 G01 商业发行候选或强行延续其原玩法。

## 6. 证据体系：避免「已有需求」变成虚假的确定性

### 6.1 每个结论至少标注

- `claim_id`，一句可核查论点。
- `source_url`，发布日期、事实发生日期、访问日期。
- `evidence_type`：官方投稿规范 / 当前平台榜单 / 历史作品目录 / 第三方统计 / 开发者自述 / 自己的实验。
- `metric_definition`：是展示顺序、游玩量、下载、DAU、收入、开发者到手收益，还是只属于公司宣传。
- `confidence`：A（近期官方/可核实时点数据）、B（独立统计）、C（自述/小样本）、D（假设）。
- `counter_evidence` 和 `expiration/recheck`（榜单和发行条款会过时）。

### 6.2 禁止发生的错误

- 把热门作品当平台**当下正在采购**的游戏类型。
- 把公司历史成功游戏当 2026 年新作。
- 把总用户规模、总下载量、平台触达写成**单款**保证流量。
- 把报价（卖方标价）写成成交价；把用户支付写成开发者净回款。
- 把源码可运行/测试通过写成真实玩家喜欢或官方批准。
- 在没有试玩视频/游戏体验时编造「完整数值」；自拟数值必须另列自有设计假设。
- 因为有 MIT 仓库便假定其图片、音频、字体均可商用。

## 7. 可证伪的核心研究与商业假设

| H | 假设 | 反证/门槛与测试（示例，不是官方成功标准） |
|---|---|---|
| H01 | 六家渠道对外开放新团队合作 | 查官方入口+实际提交/邮件回复；若仅老合作方/公司资格，则标不可进入 |
| H02 | 同一机制家族可产生具有实质差异的多款游戏 | 盲评机制树；若只是换美术/参数/关卡，则不计独立项目 |
| H03 | 成熟热门玩法更容易获得真实玩家兴趣 | 同渠道/相似曝光对照；无显著体验提升则不可用「热门」论证 |
| H04 | 第二款研发成本因为组件复用显著下降 | 同口径记录实际人力+AI+返工成本；若未下降则拆析瓶颈 |
| H05 | 自动关卡生成既能有解又有好体验 | 求解器 + 真人测试；可解但玩家觉得枯燥 → 失败 |
| H06 | Web 同一资产能适配多个渠道 | 各自构建、SDK 隔离、QA、合同冲突检查；失败要记录原因 |
| H07 | Coolmath 可以用固定非独家许可变现 | 正式报价/付费/协议；只有投稿成功不是验证 |
| H08 | Playgama 能给新游戏有意义的分销流量 | 取得按渠道实际曝光/启动/收益；不能以网络用户规模代替 |
| H09 | Poki 愿意推荐原创新作并改善收益 | 玩家测试/审查与合同；若要求排他但净回报不合理则拒绝 |
| H10 | CrazyGames Basic 具有有效测试价值 | 正常完成测试并得到可用反馈；未晋级不等于机制必然失败 |
| H11 | Azur/TapNation 愿承担真实测试/UA | 获取具体预算、谁付费、结算基数；只说支持不算验证 |
| H12 | 非独家游戏许可可以向多个买家重复销售 | 同一 IP 取得 ≥2 份相容的真实付费许可才初步支持 |
| H13 | 游戏长尾能产生超越维护成本的收益 | 按月净回款与维护成本追踪至少若干月；不能只看上线首周 |
| H14 | 发行/多渠道收入覆盖全部项目组合成本 | 纳入失败游戏成本，做组合级 ROI；负收益则暂停扩产 |
| H15 | AI Agent 工作流比自由编程更省成本 | 同复杂度对照，统计失败率、返工、QA 和总时间 |
| H16 | 完整施工图减少开发 Agent 的设计偏差 | 独立 Agent 不访问原研究背景按 GDD 施工；偏离项数量可统计 |

**Kill 原则**：可主动淘汰候选。对一个家族的坏体验、重授权困难或无法获取真实流量，要停止该家族的增量投资；保留通用制造资产，而不是为满足「每平台 5 款」而强行制作。

## 8. 商业模型和权利边界

### 8.1 分清五种交易

1. **直接投稿/展示**：允许上架，不保证推荐或收益。
2. **分销/联运**：合作网站采纳后按广告/IAP 等分成，分销商未必购买游戏本身。
3. **非独家商用许可**：多个买家可分别支付许可费，前提合同互不冲突。
4. **网页独家发行**：可能得到更强平台推广，但限制开放 Web 的重复发行。
5. **完全买断/IP 资产收购**：一次交易出售约定权利，可能损失长期授权空间。

用户的商业目标是资产及长期收益，因此**优先研究 2+3，再选择性评估 4+5**。禁止把客户指定需求、连续改稿的定制外包列为本轮主体商业模式。

### 8.2 必查合同字段

`copyright_owner`、`licensed_scope`、`territory`、`platforms`、`term`、`exclusivity`、`sublicense`、`source_code_delivery`、`derivative_works`、`engine_reservation`、`rev_share_base`、`ad_spend_recoupment`、`audit_rights`、`payments`、`minimum_promotion`、`termination`、`delisting`、`successors`。

**必须划分底层通用机制/引擎与游戏专有权利**。即便卖出某款游戏，也不应默认转让整个规则引擎、通用零件库、生产流程和非专有代码；若运行游戏需要使用通用运行时，合同另授必需的运行许可。

### 8.3 ROI 必须以全组合口径计算

```
组合贡献利润 = 所有游戏的实际净授权收入 + 实际净分成回款
            - 全部研发/素材/测试/获客/法务/维护/失败原型等成本
ROI = 组合贡献利润 / 全部投入成本
```

不允许以「假设每 1000 次游玩得到 X 美元」替代真实 RPM，也不能因为 1 款成功就忽略 9 款失败。缺数据时先输出可求范围和参数敏感性，不宣称已测得行业 ROI。

## 9. 施工流水线：Codex 项目准备模式

### T0 建立证据库
输入：仅六个目标渠道和官方链接。输出：渠道准入/合同/趋势证据表、更新日期、失效标记。禁止扩平台。

### T1 平台 → 具体对标游戏卡
每个平台挑 3–5 款**证据充分**的参考游戏；至少 2 款进行深入试玩与操作路径还原。要写出每款为什么火（有真实证据才可说）、目标受众是什么、为什么与渠道匹配，不能只列名字。

### T2 去重 → G01–G10 各自项目可行性档案
每家族至少 2 个可靠对标游戏，保留原版玩法骨架与原创变体部分的明确分界；给出发行目标和技术复杂度。允许选择 Kill，也允许发现资料不足后提出研究补证。

### T3 每款完整可施工项目档案
按第 4 节 12+ 文件规范。每项至少有真实参考流程、完整可执行规则、前 20 关或前 30 分钟数值、全部界面、素材明细、自动化测试、平台构建和发行风险。

### T4 对抗审查（必须独立）
让另一 Codex 会话扮演 QA、发行经理和法律风险研究员，逐条找问题：是否凭空数值、是否只是克隆、是否有无解关卡、是否对齐平台、是否真的可施工、是否能保留 IP。输出带文件路径的 Findings，严重问题阻塞下一阶段。

### T5 建造与渠道实验（需用户批准）
先通过最小可玩的垂直切片与真人反馈，再做完整美术及大量内容；目标不是纯技术展示而是可投稿的 Release Candidate。由正式合作方的真实回复及反馈继续决策。

**并行纪律**：不同 Codex 会话对不同 Gxx 的单独目录有写权限；通用机制库通过接口申请合并，不能多 Agent 同时覆盖。研究和 QA 角色独立于开发角色。

## 12. 当前结论：继续、调整、暂停

### 保留

- 自有机制库、规则 DSL、验证工具、自动构建与可回放 QA 的技术研发价值。
- 游戏 IP、非独家许可和分成等资产模式的商业可能性。
- 六渠道分工；具体对标和真人数据比纯 AI 想法更有用。
- 按游戏家族复用、跨平台分发，但 SDK 与合同必须隔离。

### 修正

- 不要一开始不用所有现成引擎；先按采购/发行要求选择 Cocos 或 Unity 等底座。
- 不要每平台都制造 5 款完全独立作品；应以去重后的 G01–G10 为主，维护多平台适配矩阵。
- 不把榜单视为新作利润预测，不把个别开发者盈利故事当平均回报率。
- 技术 QA 与真人好玩、商业成功分别验证。

### 暂停

- 完整从零造引擎；单 Agent 直接做 10 个成品；把 Vector Shift 立即当正式产品推进。
- 未审条款同时投给独家发行平台；以客户定制外包作为主要业务。
- 继续扩大发行平台清单；以网页平台上架自动产生收入作为商业前提。

### 下一里程碑

**得到三套完整、独立、可审计的 G01/G02/G04 施工档案，以及每个平台 3–5 个具体对标的证据卡，然后由用户筛选审批第一批真正施工游戏。** 这个阶段还不声称已经完成 10 个项目的设计，也不预设所有项目都会进入开发。
